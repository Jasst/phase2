# Roadmap

**P0** — без этого небезопасно или не работает. **P1** — нужно для реального использования.
**P2** — research.

Реальность: 87 тестов, `eval/`, `web/`, `server.py`, MCP — есть. Не хватает: auth для `/api/*`,
эпизодов, HNSW, cross-encoder, авто-склонений, проверки «Сна» на GPU, eval на реальных данных.

## Готово

- Append-only журнал с инвариантами I1–I10, битемпоральность, supersede-цепочки, `functional`-конфликты.
- Entity linking + relation normalization.
- Гибридный поиск: LSH ∪ Vector → RRF → BFS → rerank. Decay + archive.
- Экстракция фактов с дословной проверкой evidence.
- MCP-сервер (JSON-RPC 2.0, stdlib), 13 инструментов.
- LLM-бэкенды (llama.cpp, LM Studio), автозапуск и перезапуск.
- Отдельный процесс эмбеддингов + кэш + автоопределение модели.
- Планирование «сна», запись датасета, функция гейта `accept_adapter`.
- Веб-интерфейс, `/api/*`, `/mcp`. 87 тестов, `eval/` для G2/G3.

## P0

### P0.1 · Auth для `/api/*` и `/`

`/mcp` закрыт токеном, `/api/*` и `/` — открыты. При публичном домене память и чат доступны всем.

- middleware в `server.py`: `Authorization: Bearer` или `X-Api-Token`;
- токен из `PULSENET_API_TOKEN`, fallback на `TRIPLEX_MCP_TOKEN`;
- флаг `PULSENET_API_PUBLIC=1` для тех, кто за nginx;
- тест: без токена 401, с токеном 200.

**Критерий:** `/api/status` без токена — 401, с токеном — 200.

### P0.2 · Обучение «Сна» end-to-end

`sleep.train` и `sleep.accept_adapter` не проверены на GPU.

- прогнать `train-sleep` на маленькой модели (Qwen2.5-0.5B или 1.5B) с 200 шагами;
- прогнать `eval` для old-fact QA и general ppl до/после;
- вызвать `accept_adapter`, проверить accept и reject ветки;
- зафиксировать результат в `docs/sleep-run.md`: модель, шаги, gate, время.

**Критерий:** адаптер обучен, гейт вызван, accept/reject воспроизводим.

### P0.3 · Eval на реальных данных

Точность на реальных русских данных не измерена.

- расширить `fixtures/queries.jsonl` до 30–50 запросов из реального чата;
- посчитать recall@8, MRR, nDCG на `bge-m3` и на `HashEncoder` (baseline);
- зафиксировать в `eval/README.md`: модель, метрики, датасет.

**Критерий:** таблица «bge-m3 vs hash» на одних данных.

## P1

### P1.1 · Эпизодическая память

Нет контейнера «тройка связанных фактов». Факты — атомы, чанки — текст, между ними пусто.
Закрывает «триплексную ячейку» из исходной идеи и даёт основу для консолидации сценариев.

    @dataclass
    class Episode:
        episode_id: str
        fact_ids: List[str]      # упорядочены по valid_from
        valid_from: str
        valid_to: Optional[str]
        recorded_at: str
        source_doc_id: str
        summary: str             # LLM-сжатие тройки
        salience: float

- хранится в отдельном append-only JSONL (`episodes.jsonl`);
- участвует в `recall` как контекст, не только отдельные факты;
- для эпизодов отдельный `is_eligible`: консолидируются только после ≥3 эпизодов с одной (s, r).

Работы: `triplex/episodes.py`, `EpisodeStore`, подъём эпизода в `recall` при ≥2 фактах в seeds,
MCP-инструмент `triplex_episode`, тест «три факта, связанные сущностью → один эпизод».

### P1.2 · Авто-склонения

Сейчас склонения сводятся только вручную через `triplex_link_entity`.

- лемматизация через `pymorphy3` (русский) или `spaCy` (мультиязычный);
- при `link_entity` сравнивать леммы до эмбеддинга;
- записывать в `_alias_to_entity` автоматически;
- конфиг `TRIPLEX_LEMMATIZE=1|0`, fallback на текущий режим.

**Критерий:** «кота» и «кот» — одна сущность без ручного вызова.

### P1.3 · Cross-encoder reranker

`0.7·cos + 0.3·lex` — не cross-encoder.

- абстракция `Reranker` с двумя имплементациями: `LexicalReranker` (текущий) и `CrossEncoderReranker`;
- `CrossEncoderReranker` через `llama-server --rerank` с bge-reranker-v2-m3;
- конфиг `TRIPLEX_RERANKER=lexical|bge`;
- бенчмарк на `fixtures/queries.jsonl`: recall@8, MRR.

**Критерий:** bge-reranker не хуже lexical на fixtures.

### P1.4 · HNSW

`VectorIndex` — flat-cosine O(N).

- `HNSWIndex` за тем же интерфейсом `topk(vec, k, allowed)`;
- `hnswlib` или `faiss`, fallback на flat;
- бенчмарк: 10k / 100k / 1M фактов, recall@10 vs flat;
- конфиг `TRIPLEX_INDEX=flat|hnsw`.

**Критерий:** при 100k фактов HNSW не хуже flat по recall и быстрее.

### P1.5 · Документация

- `docs/architecture.md` — карта памяти;
- `docs/invariants.md` — I1–I10 с примерами;
- `docs/cookbook.md` — рецепты: «мой первый документ», «противоречие», «время», «сон»;
- `docs/decisions/` — ADR: «почему append-only», «почему один владелец», «почему эпизоды
  не консолидируются».

## P2

### P2.1 · Комплемент и зеркало

Из исходного брифа.

- `triplex_complement(fact_id)` — для симметричных отношений (`старше`↔`младше`, `родитель`↔`ребёнок`)
  создаёт обратный факт с тем же провенансом;
- `triplex_mirror(episode_id)` — обратный порядок эпизода;
- `LSHIndex.anti_topk(vec, k)` — `np.bitwise_not(code)` → ближайшие «антиподы» в 512-битном пространстве.

Зачем: отрицание на уровне онтологии, «анти-поиск» для проверки гипотез.

### P2.2 · Эпизодическая консолидация

«Сон» консолидирует не отдельные факты, а эпизоды. Приоритет эпизодам с ≥3 фактами одного `r`;
датасет — «сценарий», не «QA».

### P2.3 · Multi-hop adaptive depth

Сейчас BFS ≤ 2. Если top-1 confidence < 0.6 — углубить до 3; если на глубине 1 уже ≥3 факта
с conf > 0.8 — не углублять.

### P2.4 · Режимы B/C (kNN-LM, смещение логитов)

Из брифа. Нужны скрытые состояния модели — либо через `llama-server --logits`, либо через отдельный
forward на HF. Меняет LLM-бэкенд, не память. Сначала — research-прототип вне основного пайплайна.

### P2.5 · Bit-level Triplex

Исходная «матрица 512×512 из триплетов». Экспорт `LSHIndex.codes` как матрицы 512×512 (или больше)
для визуализации и анализа кластеров. Не для продакшна — для исследования.

## Открытые вопросы

1. **Append-only vs компакция.** Журнал растёт линейно. Нужна ли компакция (схлопывание
   `retract`-нутых фактов в снапшот) или append-only — принцип?
2. **Один владелец vs мультипользовательность.** Нужна ли мультипользовательность, или это разные продукты?
3. **τ_days для эпизодов.** Должны ли эпизоды затухать? Сейчас «эпизоды не консолидируются»,
   но затухание — отдельный вопрос.
4. **Провенанс для консолидированного.** Когда факт ушёл в LoRA, его провенанс остаётся в журнале,
   но модель «знает» его без источника. Это допустимо? Как аудировать?
5. **Формат `episodes.jsonl`.** Плоский список `fact_ids` или DAG с временными рёбрами?
6. **Reranker: локальный или облачный.** Local-first говорит «локальный», но cross-encoder тяжелее.
7. **Метрики.** Recall@k недостаточно. Нужны MRR, nDCG, «старые факты не потеряны», «противоречия разрешены».
8. **Склонения: pymorphy3 или spaCy.** Русский или мультиязычный — что важнее для v1?

## Принципы

- **Append-only.** Ничего не удаляется. `retract` — не удаление, а закрытие.
- **Один владелец.** Локально, приватно, без облака.
- **Провенанс.** Каждый факт имеет источник и позицию.
- **Детерминизм.** Replay даёт тот же `state_hash`.
- **Инварианты важнее фич.** Лучше меньше, но с I1–I10.
- **Эпизоды ≠ семантика.** Эпизоды не консолидируются. Это архитектурная граница.
